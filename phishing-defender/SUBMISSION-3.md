# 최종 3차 제출 입력 문구 — 피디(P.D.)

## 이번에 만든 것

1·2차의 스크린샷 글자 인식·위험 표현 및 실제 주소 표시·상황별 질문을 이어서, 첫 화면에 ‘이미 행동했어요’를 추가했습니다. 링크 클릭, 비밀번호·인증번호 입력, 개인정보 제공, 앱 설치, 송금 중 해당 항목을 여러 개 선택하면 분석을 기다리지 않고 대응 순서를 볼 수 있습니다. 송금 피해는 112와 금융회사 연락을 가장 먼저 보여 줍니다.

점검 결과에는 원문·스크린샷·원본 링크를 넣지 않는 요약을 만들고, 사용자가 직접 수정한 뒤 복사하거나 텍스트로 저장하게 했습니다. 기존 신고의 ‘5건이면 신고 필요’ 자동 분류 문구를 없애고, 새 제보의 접수·검토·확인·오인 신고 상태와 조회 코드 기반 정정 요청을 구현했습니다. 운영 Supabase DB에 SQL을 적용했고 공개 앱의 연결 상태를 확인했습니다. 서버가 중지되거나 연결되지 않을 때는 접수 버튼이 꺼지고 미연결 상태를 알립니다.

## 확인하는 방법 · 3단계 이내

1. 첫 화면 ‘이미 행동했어요’에서 ‘돈을 이체하거나 결제했어요’와 ‘앱을 설치했어요’를 함께 선택해 송금 대응이 먼저 나오는지 확인합니다.
2. ‘의심스러운 배송 문자’를 자동 확인하고 결과의 점검 요약에서 원문·링크 주소가 빠졌는지 살핍니다. 내용을 수정해 복사하거나 저장합니다.
3. 신고 영역에서 ‘신고 서버가 연결됐습니다’와 활성화된 접수 버튼, 조회·정정 영역을 확인합니다. 가상 번호를 이용한 실제 DB 함수 시험은 한 트랜잭션 안에서 수행한 뒤 롤백해 시험 제보가 남지 않게 했습니다.

## 바뀐 점과 그 이유

기존 앱은 링크를 누르기 전의 판단에 집중해, 이미 피해 행동을 한 사람의 긴급한 다음 조치가 뒤에 있었습니다. 그래서 화면 맨 앞에 행동별 대응을 놓았습니다. 결과 공유 때 원문과 주소를 그대로 복사할 위험을 줄이기 위해 요약에는 검출 근거와 다음 행동만 기본으로 넣었습니다.

신고 건수만으로 위험 번호를 단정하면 오인 신고나 반복 제보에 취약합니다. 새 구조에서는 사용자 제보와 운영자 확인을 분리하고, 제보자가 조회 코드로 정정 요청을 남길 수 있게 했습니다. 정정 요청은 검토 전 상태로 표시되며 즉시 사실 판정을 바꾸지 않습니다.

## AI에게 맡긴 일과 내가 판단한 일

AI에게 맡긴 일: 행동별 대응 설계·코드, 공식 피해 대응 자료 확인, 비식별 요약, 신고 상태·정정 DB 변경안, 자동 테스트·브라우저 검증·제출 문서 정리.

내가 판단한 일: 기존 피싱 방지 앱을 프리미엄 최종 과제로 이어가고, 기존 3차 범위에 ‘이미 행동했어요’와 신고 처리 상태·정정을 추가하기로 결정했습니다.

AI 모의 사용은 실제 사람의 사용성 평가로 기재하지 않습니다. 직접 사용하거나 주변 사용자에게 확인받은 결과는 실제 기록으로 보완합니다.

## 사용자에게 확인받은 결과

실제 사용자 확인은 아직 진행하지 않았습니다. AI가 가상 사용 상황으로 ‘배송 문자 자동 점검’과 ‘송금·앱 설치 후 대응’을 실행해, 링크·민감정보 요구 표시와 112 우선 안내를 확인했습니다. 실제 사용자 3~5명에게 첫 행동의 이해도, ‘접수됨’과 ‘운영자 확인’의 차이, 공유 요약의 개인정보 노출 여부를 확인할 계획입니다.

## 다음에 할 일

공개 운영 중 신고 글 보존 기간·관리자 검토·남용 방지 정책을 정하고, 실제 사용자 확인과 독립 사례 평가를 추가합니다. 아직 실제 사용자 인터뷰나 현장 피해 감소 검증은 하지 않았습니다.
